# Boorushiko — TODO / план разработки

Booru для **классического 2D-арта**. Без ИИ-генераций, без 3D/рендеров, без фотореализма.
Фронтенд и первый рабочий движок уже в репозитории: Angular 22 + Tailwind 4, Fastify 5 + SQLite.

Главная архитектурная идея: **оригиналы живут у тебя, внешние хостинги — заменяемые зеркала**.
Любое зеркало может умереть, заблокировать хотлинк или удалить файл — сайт не должен от этого ломаться.

## 0. Принципы

- [ ] Один пост = один мастер + N зеркал delivery + копия мастера в Telegram + миниатюры, сгенерированные локально.
- [ ] Ни один внешний хост не является единственной точкой отказа. Минимум 2 живых зеркала на пост.
- [ ] Мастер удаляется из staging только после подтверждённой копии в Telegram/HDD (см. §2.7);
      постоянного локального оригинала на VPS нет.
- [ ] Никаких ИИ/3D — это правило контента, а не пожелание: см. §4.
- [ ] Никакой ML-начинки на сайте: поиск по тегам, а не «похожие через эмбеддинги».
- [x] Boorushiko — **гость** на общем сервере (8 сайтов, 46 GB, свободно ~12.8 GB): **zero-disk для
      изображений** — на диске только код и SQLite (~0.6 GB), staging выносится в tmpfs через
      `STAGING_DIR`; картинки живут на зеркалах и в Telegram.
- [x] Два класса постов: `remote` (парсер, прямая ссылка на источник, копий нет) и `hosted`
      (ручная загрузка аплоадера, зеркала + Telegram). Парсерный контент не перезаливаем никогда.

## 1. Реальность выбранных хранилищ (прочитать до первой строки кода)

Проверено по официальным страницам (ссылки в §12). Коротко: **отсутствие рекламы снимает
коммерческие запреты, но не запреты на автоматизацию**. imgbb запрещает автоматизированное
использование, postimages — программные загрузки (это не про деньги), yourimageshare даёт API,
но не гарантирует хранение. Поэтому схема «залил через API и забыл» всё равно не годится:
нужен дизайн из §2 и честная оценка рисков.

| Хост                                | Что даёт                               | Лимиты                                                           | Хотлинк                       | ToS                                                                                                | Роль в проекте                               |

## 2. Хранилище и доставка изображений

### 2.1 Схема

```
Angular  ──►  API (Fastify)  ──►  SQLite (WAL, один процесс-писатель)
                  │
                  ├─► remote: /i/:id → 302 на источник, /t/:id → прокси превью + RAM-кэш
                  ├─► hosted: staging (tmpfs) → зеркала + Telegram
                  ├─► таблица jobs (очередь в той же БД)
                  ├─► sharp: превью 300 px (hosted) / 480 px (remote) + WebP/AVIF (ffmpeg нет)
                  └─► Telegram bot ──► канал (приёмник: витрина + DR, НЕ источник для сайта)
```

### 2.2 Модель данных (набросок)

```sql
posts(id, md5, sha256, ext, mime, width, height, bytes, duration_ms,
      rating, score, fav_count, source_url, artist_commentary,
      status,          -- pending | active | hidden | deleted
      storage_kind,    -- remote (hotlink) | hosted (копии на зеркалах)
      created_at, updated_at)

post_sources(id, post_id, host, remote_id, url, width, height, bytes,
             role,          -- serve (delivery) | archive (мастер-копия)
             format,        -- png | jpg | webp | avif | mp4 | webm
             status,        -- pending | ok | dead | rejected
             priority,      -- 1 = основной
             last_checked_at, fail_count, uploaded_at)

post_variants(id, post_id, kind, url, width, height, bytes, format, quality)
  -- kind: thumb300 | delivery
  -- url: только внешний; локальных файлов изображений нет (см. §2.7)
  -- format: webp | avif; quality: null = lossless / near-lossless

tags(id, name, category, post_count, is_deprecated)
  -- category: general | artist | character | copyright | species | meta
post_tags(post_id, tag_id)
tag_aliases(alias_tag_id, target_tag_id)
tag_implications(source_tag_id, target_tag_id)
pools(id, name, description, is_series)
post_relations(parent_id, child_id, kind)
post_origins(id, post_id, provider, page_url, file_url, preview_url, referer_policy,
             checked_at, status)   -- provider = адаптер: danbooru | gelbooru | pixiv;
                                   -- posts.source_url = первоисточник (pixiv/twitter)

post_backups(id, post_id, channel
  -- channel: sfw | nsfw; provider=telegram; в доставке не участвует, нужен для восстановления
  -- provider=telegram; в доставке не участвует, нужен для восстановления
jobs(id, kind, payload, run_at, attempts, locked_at)
users, sessions, comments, votes, favorites, reports, dnp_artists, audit_log
```

Индексы: `posts(md5)`, `posts(created_at desc)`, `post_tags(tag_id, post_id)`, `tags(name)`.
AND-поиск: `JOIN post_tags ... GROUP BY post_id HAVING COUNT(DISTINCT tag_id) = N`, исключения — `NOT EXISTS`.
Для `*wildcard*` — FTS5 с `tokenize='trigram'`: он же ускоряет `LIKE '%...%'` и автокомплит.

- [x] Drizzle + `better-sqlite3` (не Prisma: отдельный движок ради одного файла не нужен).
      `node:sqlite` в Node 22+ ещё меняет API — `better-sqlite3` предсказуемее.
- [x] `PRAGMA journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON`; один процесс-писатель.
- [x] Не хранить теги массивом: только нормализованные `post_tags` (+ кэш строки тегов для выдачи).
- [x] `md5` для дедупа (как у данбуру), `sha256` — для целостности и сверки с бэкапом.

Реализовано в `0001_init.sql` + `0002_users_comments.sql`: `posts`, `tags`, `post_tags`, `post_sources`,
`post_variants`, `post_origins`, `jobs`, `users`, `sessions`, `comments`. Пулы, связи постов,
алиасы/импликации и жалобы — ещё нет.

### 2.3 Резолвер ссылок и hotlink

- [x] `GET /i/:id` → 302 на первое живое зеркало (`Cache-Control: public, max-age=60`).
- [x] `GET /api/v1/posts/:id` отдаёт **массив** источников, отсортированный по `priority`/health.
- [ ] Во фронте: `<img referrerpolicy="no-referrer" (error)="nextSource()">` — браузер сам
      переключается на следующее зеркало без запроса к API.
- [ ] `referrerpolicy="no-referrer"` обязателен: 302 сохраняет Referer твоей страницы, и хост
      с анти-хотлинком может отдать 403. Проверить оба варианта (пустой Referer тоже иногда блокируют).
- [ ] Для внешних площадок (BB-код, форумы) — только `/i/:id`, чтобы ссылка не протухала.
- [ ] Проксирование через себя (`/img/:id`) — **не сразу**: это твой трафик. Включать точечно для
      хостов, которые режут хотлинк.
- [ ] **Индексный режим (`remote`).** Основная масса постов приходит от парсеров: файл не копируется,
      сайт отдаёт прямую ссылку источника. Это единственный способ дойти до миллионов при zero-disk.
- [ ] `posts.storage_kind`: `remote` (парсер, копий нет) | `hosted` (ручная загрузка, зеркала + Telegram).
- [ ] Для превью брать **уменьшенную версию у посредника**, а не оригинал: Danbooru `/preview/`,
      Gelbooru thumbnail, Pixiv `_square1200`/`_master1200`. Это 30–100 KB вместо 2 MB на прогрев кэша.
- [x] `/t/:id` для `hosted`: 300 px WebP из мастера с `Cache-Control: immutable`.
- [x] `/t/:id` для `remote`: скачать `preview_url` → sharp → 480 px WebP → отдать и положить в RAM-LRU
      128 MB. Промах = один запрос к источнику; хранить превью для 3 млн всё равно негде.
      Прокси отклоняет приватные адреса, проверяет каждый редирект, лимитирует размер и таймаут.
- [ ] Referer: по умолчанию `referrerpolicy="no-referrer"`. Если источник требует свой Referer
      (Pixiv), либо тонкий прокси с нужным заголовком, либо кнопка «открыть источник».
      Проверить каждый провайдер в Phase 0 — это решает, работает hotlink или нет.
- [ ] Региональные блоки: CDN посредников и `i.pximg.net` в РФ могут не открываться напрямую.
      Если аудитория оттуда — прокси превью обязателен, а полный файл открывать по ссылке на источник.
- [ ] Битая ссылка: помечать `source_dead`, показывать заглушку и кнопку на источник; метаданные
      и теги не удалять. Hotlink не отменяет DNP и жалобы правообладателей.
- [ ] **Полная версия `remote` не хранится нами.** Страница поста грузит large/sample прямо
      с посредника (Danbooru sample, Pixiv `_master1200`), а «оригинал» — ссылка на
      страницу источника. 2 MB на каждый просмотр отдаёт чужой CDN, а не наш VPS.
- [ ] Если источник режет хотлинк — прокси только на время запроса, без записи на диск:
      место не тратим, но трафик становится нашим. Считать лимиты VPS до включения: 10k полных
      просмотров в день × 2 MB ≈ 600 GB/мес.

### 2.4 Форматы и сжатие (WebP / AVIF)

Три разные сущности, которые нельзя путать:

| Слой         | Что это                                                  | Где живёт                                                        |
| ------------ | -------------------------------------------------------- | ---------------------------------------------------------------- |
| **мастер**   | байты ровно как загрузили, `sha256`, без перекодирования | внешний HDD + Telegram (только `hosted`; у `remote` мастера нет) |
| **delivery** | WebP/AVIF, который видят посетители                      | зеркала (только `hosted`)                                        |
| **превью**   | 300 px WebP (`hosted`) / 480 px WebP (`remote`)          | зеркало (`hosted`) или RAM-кэш (`remote`)                        |

- [ ] **Мастер не перекодировать.** «Без потери качества» при lossy-сжатии невозможно, а lossless-WebP
      для плоского линейного арта часто **больше** PNG (на 5–15%): у PNG уже идеальное сжатие
      больших однотонных областей.
- [ ] Сравнивать размеры по каждому файлу и брать меньший из `png / webp-lossless / webp-near-lossless / avif`.
      Если все варианты больше мастера — отдавать мастер.
- [ ] Рабочие пресеты: скетчи и line art — WebP near-lossless (q80, nearLossless 60);
      иллюстрации с градиентами и тенями — AVIF q50–65 (обычно в 2–4 раза меньше PNG).
- [ ] Альфу не сплющивать: WebP и AVIF её поддерживают, JPEG — нет (потеря прозрачности = брак).
- [ ] GIF: короткие — animated WebP; длинные (>5 c или >10 MB) — MP4/WebM, но тогда теряется автоплей,
      как у гифки. Решить на реальных примерах в Phase 0.
- [ ] Отдавать через `<picture>`: `image/avif` → `image/webp` → оригинал. Fallback бесплатный, без JS.
      Поддержка AVIF: Chrome 85+, Firefox 93+, Safari 16.4+ — на 2026 покрытие достаточное.
- [ ] Кнопка «скачать» ведёт на **мастер**, а не на delivery. Если мастер не на VPS — отдавать через
      контролируемый download-эндпоинт, а не прямой ссылкой на архив.
- [ ] У delivery можно срезать EXIF/XMP для экономии, у мастера — **нельзя** (нужен для §4 и атрибуции).
- [ ] AVIF считается долго: ~0.3–1 c CPU на кадр 1080p и единицы секунд на 4K. На 2 vCPU это заметно,
      поэтому только очередь, `concurrency=1`, никогда внутри HTTP-запроса.
- [ ] На слабой машине AVIF можно не делать вовсе: WebP кодируется в 5–10 раз быстрее. Отдавать
      WebP + мастер — уже нормальный результат, AVIF добавить позже батчем.
- [ ] Арифметика: 100k постов × 2 MB PNG ≈ 200 GB мастеров, delivery при 200–350 KB ≈ 20–35 GB.
      На диске сервера из этого не оседает ничего: мастер — HDD + Telegram, delivery и превью —
      зеркала, локально только tmpfs на время обработки (см. §2.7, §8.2).
- [ ] `md5` считать по мастеру: дедуп с другими буру работает только по исходным байтам.
- [ ] На зеркала уходит delivery (`role=serve`) только у `hosted`; у `remote` зеркал нет вообще.

**Видео: льём как есть, без транскодинга.** ffmpeg не нужен вообще.

Видео на 2D-буру мало (основной объём — r34, а там в основном 3D, которое мы не берём), поэтому
перекодировать нечего. Отдаём исходный файл, а всё нужное для показа делает браузер.

- [ ] Принимаем только `mp4` (H.264) и `webm` (VP8/VP9/AV1), проверяя воспроизводимость в браузере
      (`canPlayType`) — иначе получим «файл принят, но не играет».
- [ ] Постер и длительность снимает браузер загружающего (`<video>` + `<canvas>` → WebP 300 px);
      сервер проверяет magic bytes/контейнер и лимиты. Постер — косметика, контентом не считается.
- [ ] Потолок 200 MB (лимит yourimageshare). Второе зеркало — catbox (200 MB, некоммерческий ок);
      imgbb видео не умеет.
- [ ] Копия в Telegram — до 50 MB (`sendDocument`), но вытащить обратно hosted-ботом можно только
      ≤20 MB. Видео 20–50 MB имеют копию, но не восстановимы без локального Bot API server (2 GB); >50 MB — сразу `no_backup`.
- [ ] Транскод, склейку и серверный постер не делаем: GStreamer и libvlc тяжелее при тех же кодеках,
      `ffmpeg.wasm` медленнее, а свой декодер H.264/VP9 — годы работы и патенты. Не наш масштаб.
- [ ] ImageMagick/GraphicsMagick не тащить: `sharp` быстрее и памяти ест меньше.

### 2.5 Пайплайн загрузки

- [x] Валидация по magic bytes, а не по расширению; whitelist: jpg/png/gif/webp/avif, видео mp4/webm.
- [x] Потоковая обработка: хеши считаются по потоку, staging в tmpfs, варианты уходят наружу.
- [x] Лимит размера: 32 MB для картинок (общий знаменатель imgbb). Для видео 200 MB — после
      включения видео; сейчас загрузка изображений.
- [x] Дедуп по `md5` → «этот пост уже есть» со ссылкой.
- [x] Миниатюры картинок — `sharp` (libvips, готовый бинарник, без ImageMagick и сборки из исходников).
- [ ] Видео: файл идёт как есть, без перекодирования. Браузер отдаёт постер 300 px и длительность,
      сервер проверяет контейнер и лимиты, кладёт в tmpfs и сразу отправляет на зеркала (см. §2.4).
- [ ] Загрузка на зеркала — через очередь, с per-host token bucket:
      yourimageshare 20/min и 500/день, imgbb ~1 rps (квоты не опубликованы — быть консервативным).
- [ ] Публикация только когда **≥2 зеркала вернули OK**; иначе `pending` c пометкой.
- [ ] Ретраи с backoff, идемпотентность по `idempotency_key = sha256(post_id + host)`.
- [ ] postimages: задача «выгрузить вручную» в админке + поле для вставки готовой ссылки. Не автоматизировать.
- [ ] Мастер не перекодировать никогда; delivery-версии готовятся отдельно (см. §2.4) и только они
      идут на зеркала `role=serve`.
- [x] `remote`-посты проходят короткий путь: origin + метаданные + теги → `active`, без staging
      и без зеркал. Долгая часть (скачивание, превью) — лениво при первом показе.

### 2.6 Health-check зеркал

- [ ] Cron каждые 6 часов: выборка 200 случайных постов, `HEAD`/`Range: bytes=0-0` по каждому источнику.
- [ ] `403/404/410` → `fail_count++`; после 3 подряд → `dead`, пост в очередь «перезалить».
- [ ] `5xx`/таймаут — не считать смертью, ретрай позже.
- [ ] Полный аудит раз в неделю + дашборд: живых зеркал на пост, по хостам, топ «хрупких».
- [ ] Проверять и превью 300 px: если превью умерло при живом мастере — перегенерировать из мастера
      и залить заново (это дешёвая операция, в отличие от восстановления самого файла).
- [ ] Для `remote` проверять `file_url`/`page_url` источника: `403/404` → `source_dead`.
      Перезалить нечего (копии нет) — только пометить и, если есть, предложить архивную ссылку.
- [ ] Перезалив: файл ещё в tmpfs → иначе восстановление из Telegram (§3) → залить на живой хост → обновить `post_sources`. Локальных мастеров нет.
- [ ] Алерт в Telegram-чат админа, если у >5% постов осталось <2 зеркал.

### 2.7 Zero-disk: где живут байты

Изображения не хранятся на диске постоянно — ни мастера, ни превью; staging живёт в tmpfs.

- [x] Staging — настраиваемый `STAGING_DIR`: в проде `/dev/shm/booru` (512 MB без видео, 1 GB если
      видео включено). Каталога `storage/` для изображений не существует.
- [ ] Порядок: приём в tmpfs → хеши и размеры → **мастер сразу в Telegram** (`sendDocument`) →
      delivery на 2 зеркала → превью 300 px на зеркало → удаление из tmpfs.
      Telegram здесь — durable-лог: если процесс упадёт посреди заливки, файл уже сохранён.
      Сейчас порядок без Telegram: staging → зеркала → удаление.
- [x] TTL 60 минут: не подтвердился `MIN_MIRRORS` — пост `failed`, staging очищается.
- [ ] tmpfs ест RAM, а не диск: учитывать в `max_memory_restart`, больше не выделять.
      При перезагрузке tmpfs теряется, поэтому Telegram-копия должна появляться раньше зеркал.
      Для видео >50 MB это невозможно — такие посты помечаются `no_backup`.
- [ ] Канонические копии: внешний HDD (rsync с домашней машины) + Telegram-канал.
      Порядок восстановления: HDD → Telegram → зеркало.
- [ ] У `remote` единственная копия файла — у источника. Это осознанная плата за миллионы постов:
      место не тратим, но и восстановить файл, если источник его удалил, не сможем.
- [ ] Ежедневный снапшот базы через `VACUUM INTO` (~250 MB) — единственное, что реально занимает место.
      При свободных <1 GB стримить бэкап на HDD/в B2 без локальной копии.
- [ ] Правило 3-2-1: VPS (только БД) + внешний HDD + Telegram-канал.
- [ ] Раз в месяц — тестовое восстановление 10 случайных постов из бэкапа (учёт в чеклисте).
- [ ] Мониторинг: свободное место, размер tmpfs, размер БД; алерт при <2 GB свободных.

## 3. Telegram: приёмник, витрина и восстановление

Telegram **не участвует в доставке**: сайт никогда не грузит картинки из канала, канала нет
в `post_sources` и в резолвере. У него три другие роли:

1. **Публичная витрина с работающим фильтром по тегам.** Хештеги (`#flandre #solo`) дают поиск
   внутри Telegram, а каждый пост ведёт на страницу сайта — это канал привлечения людей, а не хранилище.
2. **Оффсайт-копия мастера.** Если VPS умрёт, файл останется в канале.
3. **Источник восстановления.** Когда зеркало отдало 404, а локального мастера уже нет, файл
   забирается из Telegram и заливается на новый хост.

- [ ] В канал уходит **мастер** (оригинальные байты), а не WebP/AVIF-delivery: delivery можно
      пересобрать, мастер — нет.
- [ ] В канал дублируются только `hosted`-посты: у `remote` копии нет, отправлять нечего.
      Для них в канале максимум ссылка на пост сайта.
- [ ] `sendDocument`, **не** `sendPhoto`: фото Telegram пережимает и режет по размеру,
      документ сохраняет байты как есть.
- [ ] Капшн: `#<post_id> <artist> <copyright>` + хештеги тегов + ссылка на пост (с UTM).
      Лимит капшна — 1024 символа, длинные наборы тегов обрезать по приоритету.
- [ ] В БД хранить **публичную ссылку** `t.me/<channel>/<message_id>` (`post_backups`),
      а `file_id` — только как кэш для быстрой переотправки.
- [ ] Ссылка и есть ключ восстановления: даже при потере БД достаточно списка `t.me/...` из бэкапа.
- [ ] Восстановление: бот, состоящий в канале, по `from_chat_id=@channel` + `message_id` делает
      `copyMessage`, получает актуальный `file_id` → `getFile` → скачивает → заливает на живой хост.
      Поведение зависит от прав бота — проверить на своём канале.
- [ ] Лимиты Bot API: `sendPhoto` 10 MB, `sendDocument` 50 MB, `getFile` на скачивание 20 MB.
      Файлы >20 MB ботом не вытащить → локальный Bot API server (до 2 GB) на VPS, отдельной задачей.
- [ ] Альбомы (`sendMediaGroup`) — до 10 файлов, для пулов и серий.
- [ ] **Два канала:** основной (SFW) и второй (18+). Маршрутизация по `posts.rating`: `e` → NSFW.
- [ ] Каналы не связывать forward-ами; NSFW помечен 18+, в описании — правила и ссылка на сайт.
- [ ] В `post_backups.channel` хранить, в какой именно канал ушла копия.
- [ ] Алерты админу — в отдельный приватный чат, не в публичный канал.
- [ ] Проверить требования Telegram к публичным каналам с 18+ контентом и отметить канал соответствующим образом.
- [ ] Токен бота — только в env на сервере, никогда в Angular.

### 8.1 Ресурсы: что есть и что реально упирается

Сейчас **4 vCPU / 24 GB / 46 GB**, свободно ~12.8 GB. CPU и RAM с большим запасом; диск общий с соседями.
Проектировать надо от него, а не от «сколько потоков выдержит».

| Компонент              | В покое   | Пик                     |
| ---------------------- | --------- | ----------------------- |
| Fastify + SQLite (WAL) | 60–120 MB | ~200 MB                 |
| sharp / libvips        | 0         | +100–200 MB на операцию |
| AVIF-воркер, 1 поток   | 0         | +100–300 MB             |
| Caddy                  | ~20 MB    | ~40 MB                  |

- [ ] 24 GB RAM не значит «кэшируй всё в память»: после рестарта кэш пустой, а диск — постоянный.
      Всё, что должно пережить рестарт, живёт в SQLite или на зеркалах.
- [ ] Кодирование — `concurrency=1`: ядра общие с восемью соседними сайтами, а очередь всё равно
      ограничена 500 загрузками/день на yourimageshare. Запуск через `nice -n 10`, диск — `ionice -c2 -n7`.
- [ ] RSS: цель 120–200 MB, потолок 400 MB. В pm2 `max_memory_restart: 400M`: лучше рестарт нашего
      процесса, чем OOM-killer, который выберет жертву среди соседей.
- [ ] Если хостинг придётся менять: важнее диск, а не ядра. Минимум для этого приложения —
      1–2 vCPU / 1–2 GB / 20 GB, если превью вынесены или их немного.
- [ ] Замерить в Phase 0: время AVIF для 1080p и 4K, пик RSS на 10 превью подряд, вес одного превью.

### 8.2 Диск: zero-disk для изображений (~0.6 GB)

Свободно 12.8 GB из 46, но квота всё равно жёсткая: рост нашего сайта не должен зависеть
от свободного места соседей. Изображения на диск не попадают вообще.

| Что                          | Лимит             | Примечание                        |
| ---------------------------- | ----------------- | --------------------------------- |
| Код + production-зависимости | 250 MB            | `npm ci --omit=dev`, без Docker   |
| SQLite + WAL                 | 250 MB            | ~50k постов; `VACUUM` раз в месяц |
| Логи                         | 100 MB            | pm2-logrotate, 7 дней, 10 MB      |
| **На диске**                 | **~0.6 GB**       | и не растёт с числом постов       |
| tmpfs staging                | 512 MB / 1 GB RAM | не диск; TTL 60 минут             |
| Мастера (только `hosted`)    | ~200 GB           | внешний HDD + Telegram            |
| Delivery (только `hosted`)   | 20–35 GB          | зеркала                           |

- [ ] **Правило zero-disk:** ни один байт изображения не пишется на диск. `du` каталога приложения
      не зависит от количества постов — только БД и логи.
- [x] Превью: у `hosted` генерируется в tmpfs и уходит на зеркало (отдаётся через 302);
      у `remote` — только на лету и только в RAM-кэше 128 MB, на зеркала не заливается.
- [ ] Видео не декодируется на сервере вообще: нет ни ffmpeg, ни кадров, ни транскодинга.
- [ ] Нет дискового кэша и вытеснения: единственный кэш — tmpfs 128 MB, он теряется при рестарте.
- [ ] Место занимает только БД: `VACUUM INTO` даёт +250 MB на пике, делать при свободных >1 GB.
- [ ] WAL не растёт бесконечно: `wal_autocheckpoint`, периодический `PRAGMA wal_checkpoint(TRUNCATE)`.
- [ ] Квота ~0.6 GB рассчитана на ~50k постов. На 3 млн только SQLite займёт 3–5 GB — см. §8.4.

### 8.3 Деградация и домашний воркер

- [ ] Триггеры read-only: свои каталоги >0.8 GB, `df` свободно <1 GB или pm2 перезапускал процесс
      по памяти чаще раза в час. В read-only сайт только читает и редиректит на зеркала.
- [ ] Если станет тесно: кодирование и заливку унести на домашний воркер с HDD; VPS — только API и SQLite.
- [ ] Всё состояние восстановимо из `VACUUM INTO` + Telegram/HDD, поэтому VPS — расходник:
      пересоздать на другом хостинге и развернуть за вечер.

### 8.4 Масштаб 2–3 млн постов: арифметика, которая меняет план

2–3 млн — это не «чуть больше», а другой проект. Считаем честно:

| Что                                  | 100k     | 1 млн      | 3 млн       |
| ------------------------------------ | -------- | ---------- | ----------- |
| Мастера (2 MB)                       | 200 GB   | 2 TB       | 6 TB        |
| Delivery (200–350 KB)                | 20–35 GB | 200–350 GB | 600 GB–1 TB |
| Строк в `post_tags` (~15/пост)       | 1.5 млн  | 15 млн     | 45 млн      |
| Размер SQLite                        | ~0.25 GB | ~1.5 GB    | ~3–5 GB     |
| Загрузок на зеркала (всё копировать) | 100k     | 1 млн      | 3 млн       |

- [ ] **Бесплатные хосты 3 млн копий не выдержат.** yourimageshare — 500 загрузок/день на ключ,
      это ~182k в год: 3 млн займут ~16 лет. У imgbb квоты не опубликованы, но 3 млн загрузок почти
      гарантированно приведут к бану. Поэтому копии — только для `hosted`, а не для всего каталога.
- [ ] **Диск тоже не выдержит:** 3–5 GB только под SQLite — больше всей квоты §8.2. Придётся
      поднимать квоту (договариваться с соседями) или выносить БД отдельно.

**Решение: гибрид.** Парсерный контент — индекс без копий, ручные загрузки — полноценные зеркала.

- [ ] `remote` (парсер) — hotlink источника, миллионы постов, ноль места под файлы.
      `hosted` (аплоадеры) — staging, 2 зеркала, Telegram, HDD: этих постов тысячи, и они критичны.
- [ ] Плюсы гибрида: нет 16 лет загрузок на 500/день, нет 6 TB мастеров, БД — единственное, что растёт.
- [ ] Минусы: зависимость от источника, региональные блоки, гниение ссылок, чужая Referer-политика.
      Компенсируем прокси превью, `source_dead`, кнопкой «открыть источник» и DNP.
- [ ] **Путь 1 — индекс** выбран для парсера; **путь 3 — ограниченные копии** для hosted;
      **путь 2 (B2)** держим как апгрейд для hosted, если тех станет десятки тысяч.
- [ ] Гибрид снимает вопрос «где хранить 3 млн»: их не надо хранить, надо уметь показать.
- [ ] Гибрид меняет «место» на «трафик»: полные версии `remote` идут с источника напрямую.
      Если придётся проксировать (Referer/блокировки), каждый просмотр — 2 MB через VPS;
      при 10k просмотров/день это ~600 GB/мес, что уже сравнимо с лимитами недорогих VPS.

- [ ] План: 100–200k `remote` в первый год плюс `hosted` от аплоадеров; B2 рассматривать, только
      если hosted перевалит за десятки тысяч.
- [ ] Модерация 3 млн — это ~8000 постов/день. Руками невозможно: только доверенные боты, выборочные
      проверки и жалобы. Ещё один аргумент начинать меньше.

## 10. Решения (зафиксировано)

1. **18+** — да. На сайте фильтр Safe / Mixed / Adult с подтверждением возраста; в Telegram два канала:
   основной и 18+.
2. **Кто загружает** — парсер-боты и одобренные аплоадеры по заявке. Открытой регистрации с загрузкой нет.
3. **Видео** — не в MVP: сначала картинки и GIF, видео отдельной фазой. Схема — как есть, без транскодинга,
   до 200 MB, копия в Telegram до 50 MB.
4. **i18n** — RU/EN сразу, **английский по умолчанию** (основная аудитория — EN); теги остаются
   английскими. Языки живут в реестре `LANGUAGES`, новый добавляется одной записью.
5. **Название** — Boorushiko, домен свободен.
6. **Мастера** — только внешний архив (HDD) + Telegram, на VPS их нет.
7. **Объём** — 2–3 млн через индекс (`remote`), ручные загрузки — тысячи `hosted` (см. §8.4).
   Старт — 100–200k и замер стоимости.
8. **Стартовая база** — Danbooru- и Gelbooru-импорт уже работают; Pixiv набирает базу по мере
   готовности (Phase 7).
9. **Модель хранения** — гибрид: парсерный контент hotlink-ом без копий, ручные загрузки — на зеркала
   с копией в Telegram.
10. **Источники** — Danbooru + Gelbooru → Pixiv. Twitter/X не парсим: он не даёт нормальных тегов,
    его API платный и ограничивает архив/редистрибуцию. X попадает только как `sourceUrl` из постов
    посредников или через ручную загрузку X-only.

Осталось решить:

- [ ] Правовая рамка прямого Pixiv API (официального публичного API нет) и собственных обходов.
- [ ] Правила атрибуции: что делать, если автор просит убрать (DNP) и как быстро реагировать.
- [ ] Политика хостингов к NSFW — от неё зависит, куда вообще можно зеркалить `rating:e`.
- [x] Публичный read-API для сторонних клиентов есть и документирован; ключи с quotas/audit нужны
      только когда появится внешний потребитель записи (сейчас запись — только `UPLOAD_TOKEN`).

## 11. Что осознанно НЕ делаем

- Не строим на S3 сейчас. Если понадобится — **B2 ($6/TB), не R2 ($15/TB)**: при бесплатном egress
  разница только в цене хранения.
- Не отдаём lossy-WebP/AVIF под видом «оригинала»: мастер всегда отдельно.
- Не используем ИИ ни для тегирования, ни для «похожих», ни для модерации.
- Не поддерживаем 3D-вьюер, PBR, видео-панорамы.
- Не автоматизируем postimages — их ToS это прямо запрещает.
- Не считаем внешнее зеркало архивом: у `hosted` мастер — внешний HDD + Telegram, у `remote` копии нет
  осознанно (см. §8.4).
- Не тащим ImageMagick, GStreamer, libvlc и не пишем свой видеодекодер.
- Не транскодируем видео вообще: либо принимаем как есть, либо не принимаем.

### Что из этого следует

- [ ] **Сначала кросс-источниковый дедуп, потом новые источники.** Сейчас ключ дедупа —

- [ ] **1. Pixiv** — следующий адаптер: максимальная отдача, но самый рискованный по ToS.
